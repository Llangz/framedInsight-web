# Platform Overview

> **Scope of this document set.** These docs were generated by cloning the live `framedInsight-web` repository at the latest commit and cross-checking three independent sources against each other: the live database export in `docs_source/` (table/trigger/view/function/policy dumps pulled from the running Supabase project), the SQL migration history in `supabase/migrations/`, and the actual application code in `app/`, `lib/`, and `components/`. Where these three sources disagreed, that disagreement is called out explicitly rather than silently resolved — see [Known Drift Between Migrations and Live Database](#known-drift-between-migrations-and-live-database) below. Treat the live database export as the source of truth for "what exists today"; treat the migrations as the source of truth for "why it exists."

## 1. What framedInsight Is

framedInsight is a multi-enterprise farm management platform for Kenyan agriculture, built by a working coffee cooperative committee chairman and former factory manager who is also its founder/developer. It is **not** a single-crop app — a farm can run any combination of four enterprises (coffee, dairy, poultry, small ruminants) under one account, and a farm can additionally be **owned and managed by a cooperative** rather than by an individual smallholder. The platform's two structural bets are:

1. **Multi-tenant, multi-enterprise from day one.** A `farms` row carries a `farm_types text[]` array (e.g. `{coffee,dairy}`), and every enterprise's tables hang off `farm_id`. There is no separate "app" per enterprise — it's one schema, one auth system, one dashboard shell with enterprise-specific sub-routes.
2. **Cooperative-aware ownership, not just individual smallholder ownership.** A farm can be `is_coop_managed = true`, pre-registered by a cooperative officer before the actual farmer ever signs up, and later **claimed** by that farmer via OTP-verified phone matching. This is the technical answer to a real operational problem: cooperative field officers map member farmers' plots long before those farmers have (or want) a smartphone account.

## 4. Multi-Tenant / Ownership Model

```
                      ┌────────────────┐
                      │  cooperatives  │
                      └───────┬────────┘
                              │ 1
                ┌─────────────┼──────────────────┐
                │ many                            │ many
        ┌───────▼────────┐               ┌────────▼─────────┐
        │ coop_factories  │               │cooperative_officers│
        │ (washing stns,  │               │ (admin | officer) │
        │ milk coolers…)  │               └────────┬──────────┘
        └────────┬────────┘                        │ user_id → auth.users
                  │                                 │
                  │ optional                        │ grants access to all
                  ▼                                 ▼ farms under managed_by_coop_id
        ┌───────────────────────────────────────────────────┐
        │                       farms                        │
        │  managed_by_coop_id, coop_factory_id,               │
        │  is_coop_managed, claim_token                       │
        └───────────────────────┬───────────────────────────┘
                                 │ 1
                                 │ many
                        ┌────────▼─────────┐
                        │  farm_managers    │  (user_id, farm_id, role)
                        └───────────────────┘
                                 │
                    enterprise tables (coffee_plots, cows,
                    poultry_batches, small_ruminants, …)
                    all FK to farms.id
```

Two independent access paths exist to the same `farms` row, and **RLS policies OR them together**:

- **Individual ownership**: a row in `farm_managers` linking `auth.uid()` directly to `farm_id`.
- **Cooperative ownership**: the farm's `managed_by_coop_id` matches a cooperative the requesting user is an officer of (via `cooperative_officers`).

The shared helper function `can_manage_farm(p_farm_id uuid)` checks *both* paths and is what almost every RLS policy in the schema delegates to. See `docs/database/rls-policies.md` for the full breakdown, and `docs/cooperatives/cooperative-module.md` for how a farm moves from "cooperative-mapped, unclaimed" to "claimed by its real owner."

## 5. Authentication Model

Authentication is phone-first, not email-first — appropriate for the target user (a smallholder farmer in rural Kenya, who may not have a stable email address but always has a phone number for M-Pesa). The flow:

1. **OTP request** (`/api/auth/send-otp`) — generates a 6-digit code, stores it in `phone_otp_codes` (keyed uniquely by phone number, so requesting a new OTP overwrites/deletes the old one), sends it via SMS (Tiara Connect / Africa's Talking).
2. **OTP verification** (`/api/auth/verify-otp`) — checks the code against `phone_otp_codes`, then bridges into Supabase Auth using a **"ghost email" + derived password** scheme: since Supabase Auth is email/password-native, the app derives a synthetic email and a salted password from the phone number rather than requiring the farmer to ever see or type either.
3. **Ghost-password salt isolation** (`auth_phone_salts`) — the salt used to derive the ghost password is stored in its own table, keyed purely by phone number, with RLS enabled but **zero policies** (service-role-only by design). This was deliberately *not* added as a column on `farm_managers`, because `farm_managers` doesn't have a row for a phone number until *after* OTP verification succeeds — for a cooperative-mapped farmer who hasn't claimed their farm yet, that row might not exist for months.
4. **Farm provisioning RPC** — once verified, the client calls one of two SECURITY DEFINER RPCs depending on signup type: `create_farm_with_manager` (individual farmer) or `create_cooperative_with_officer` (cooperative officer). Both are **idempotent and claim-aware** — see `docs/database/functions-reference.md` for why that matters and what bug it fixed.

## 6. Event Sourcing & Offline-First Design

Two complementary "write-ahead" patterns run through the platform:

- **`farm_events`** (server-side event log) — an append-style table (`event_type`, `event_data jsonb`, `actor_type` constrained to `user | system | mobile_app | ai_service`) originally built as the audit trail for EUDR assessments and compliance changes, with `synced_to_server` to support reconciling events captured while offline. In practice, the **separate, more general `traceability_events` ledger** (added later, hash-chained, append-only via `DO INSTEAD NOTHING` rules blocking UPDATE/DELETE) has become the audit trail of record for the coffee supply chain specifically — see `docs/architecture/traceability-architecture.md`. `farm_events` is still live and still written to, but its originally-planned consumer view (`v_eudr_assessment_stream`) is not present in the current live database (see drift note below), so treat `farm_events` today as raw material for future event-sourced views rather than a fully wired pipeline.
- **Client-side offline sync** (`lib/offline-db.ts`, `lib/offline-sync-crdt.ts`) — IndexedDB-backed local writes with Lamport-clock-style conflict resolution, reconciled server-side by the `sync-offline-events` edge function. This is what lets a cooperative field officer keep mapping farms in an area with no signal and sync later.

Each enterprise's dashboard section is gated behind `farm_types` containing that enterprise, and (for cooperative users) behind which farms they're allowed to see via `cooperative_officers`.

## 8. Background Jobs

There are genuinely **two separate schedulers** doing different jobs, which is easy to miss if you're only looking at one of them:

| Scheduler | Job | Frequency | What it does |
|---|---|---|---|
| **pg_cron** (inside Postgres, `cron` schema) | `process-message-queue-every-minute` | every 1 minute | Runs `SELECT invoke_process_message_queue();`, a SQL function that fires an HTTP POST (via the `pg_net` extension) to the `process-message-queue` edge function, which drains `message_queue` (inbound WhatsApp messages waiting for intent-parsing/response). |
| **Vercel Cron** (`vercel.json`) | `/api/cron/ews` | daily at 03:00 | The Early Warning System push: queries `alerts` for unsent, unacknowledged rows (oldest-first, capped at 200 per run to avoid a single run timing out after an outage), groups by farm, and pushes them via WhatsApp (LipaChat). |

> ⚠️ **Verification note**: the `process-message-queue` edge function that `invoke_process_message_queue()` calls is **not present** in `supabase/functions/` in this repository — only `check-eudr-risk`, `fetch-plot-indices`, `fetch-weather-data`, `send-otp`, and `sync-offline-events` are version-controlled there. It is clearly deployed and running (pg_cron is actively configured to call it every minute), but it appears to have been deployed directly rather than checked in. Worth pulling down and committing for version-control parity, the same way `20260621_claim_flow_and_rpc_fixes.sql` was retroactively documented after being applied directly.

## 9. Subscription / Tiering

Farms carry `subscription_tier` (`free` default at the table level, though the provisioning RPCs set new signups to `'smallholder'`), `subscription_start_date`, `subscription_end_date`, plus a `trial_end_date` column added later for free-trial tracking. Tier logic and feature gating live in `lib/tiers.ts` and `lib/subscription.ts`. The `v_active_subscriptions` view (see `docs/database/views-reference.md`) derives a live `active | trial | grace | expired` status per farm from these dates, which is what billing/UI screens should query rather than re-deriving the date math themselves.

## 10. Known Drift Between Migrations and Live Database

Documentation built only from `supabase/migrations/*.sql` would be **wrong in several places**, because not every file in that folder was actually applied to the live database, and at least one live table was later superseded. These were caught by diffing the live schema export (`docs_source/schema_tables.md`, `docs_source/views.json`) against migration file contents — flagging them here once, centrally, instead of repeating the caveat in every module doc:

- **`materialized-views.sql`** (no date prefix — the Supabase CLI only auto-applies files matching `<timestamp>_name.sql`, so this likely never ran via the CLI) defines `v_eudr_summary`, `v_plot_status`, `v_daily_production_new`, `v_compliance_timeline`, and `v_active_alerts`. **None of these exist in the live database.** It also references a `dairy_records` table that doesn't exist anywhere in the live schema, which strongly suggests this file is an early draft that was superseded by the `v_farm_summary` materialized view (which *is* live, added properly in the dated `20260612_materialize_farm_summary.sql`) before this one was ever deployed.
- **`create_otp_table.sql`** (also no date prefix) defines `check_otp_rate_limit()`, `increment_otp_attempts()`, and `auto_delete_on_max_attempts()` plus its trigger. Cross-referencing the live function and trigger exports: `auto_delete_on_max_attempts` and its trigger are confirmed absent live (nothing alphabetically before it in the public-function list was truncated, so this isn't an export artifact). `increment_otp_attempts` is also absent from where it should sort in the function list — and **the app calls it via `admin.rpc('increment_otp_attempts', …)` in `app/api/auth/verify-otp/route.ts` without checking the error**, which would fail silently if the function genuinely isn't deployed. This is worth a direct `\df public.increment_otp_attempts` check against the live database — if it's missing, brute-force-attempt tracking on OTP verification is currently a no-op.
- **`20260428_create_farm_events.sql`** defines `v_eudr_assessment_stream` as a consumer view over `farm_events`. Not present live — `farm_events` itself is live and written to, but this particular view was not (or was dropped).
- **`coffee_diseases`** table, created in `20260428_create_coffee_diseases.sql`, **no longer exists** in the live schema. It was superseded by the combination of `coffee_scouting_records` (field observations) + `coffee_disease_thresholds` (regional action thresholds) + `coffee_pest_library` (reference data) — a more structured model than the original flat disease-report table. If `app/api/coffee/diseases/route.ts` still references the old table name anywhere, that's worth a direct check.
- **`process-message-queue`** edge function — see §8 above.

None of this is a criticism of the migration history — it's a normal artifact of iterating fast directly against a live Supabase project (a pattern this codebase already leans on deliberately, per the established practice of patching `database.types.ts` by hand rather than always regenerating it). It's flagged here so future documentation work — human or AI — doesn't accidentally treat every `.sql` file in `supabase/migrations/` as automatically representing current reality.
