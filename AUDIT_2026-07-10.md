# FramedInsight — dead-page root cause, offline audit, UX notes
_Reviewed at commit `27c32e0` (2026-07-10)_

## 1. Why the three screenshots still show "This page didn't load"

All three (`/dashboard/coffee`, `/dashboard/coffee/eudr-check`,
`/dashboard/poultry/health`) are hitting `app/dashboard/error.tsx`, the
route-segment error boundary added a few commits ago. That boundary is
doing its job — it's surfacing real Postgres/PostgREST errors instead of
hiding them. The bug is upstream, and it's two separate things:

**a) The last commit fixed the wrong dashboard.**
`27c32e0`'s commit message says "fixed dead pages (eudr, poultry health
and coffee dashboard)," but the diff only touches
`app/dashboard/cooperative/page.tsx` and
`app/dashboard/cooperative/eudr/page.tsx` — the **cooperative** dashboard.
The screenshots are all `/dashboard/coffee/**` and `/dashboard/poultry/**`
— the **farmer** dashboard. Two different route trees, two different
`page.tsx` files. The farmer-side pages were never touched by that
commit. This diff fixes the actual file for the coffee overview page
(`app/dashboard/coffee/page.tsx` — see below); the EUDR and poultry
health pages turn out not to need a code fix at all (part b).

**b) Two migrations that already fix the real root cause exist in the repo but were never run against the live database.**

- `supabase/migrations/20260711_fix_secondary_materialized_views.sql`
  fixes `/dashboard/coffee/eudr-check`: `v_compliance_timeline` (and 4
  sibling materialized views) never had `GRANT SELECT` for `authenticated`
  — every read from the app was a 403 the moment the "graceful
  degradation" `unwrap()` migration stopped silently swallowing it. This
  file **is in git** as of `27c32e0` but until it's actually run against
  the database, the page will keep crashing exactly like the screenshot.
- `supabase/migrations/20260710_reload_postgrest_schema_cache.sql`
  explains `/dashboard/poultry/health`: PostgREST's schema cache didn't
  pick up the columns added in `20260709_add_poultry_health_mortality_fields.sql`
  until told to reload. Also already in git, also not yet applied.

**Action required (I can't do this part — no database access from here):**
```
supabase db push
```
or run both files' SQL directly in the Supabase SQL editor, then hard-refresh.
If `supabase db push` reports these as already-applied, check the
migration history table (`supabase migration list`) against what's
actually live — it's possible these were written but the push failed
silently or targeted the wrong project ref.

**c) `/dashboard/coffee` (the overview) was a real code bug, now fixed in this diff.**
`v_farm_summary` is a materialized view refreshed on a 1-minute
`pg_cron` tick, not a live view. The old code used `.single()`, which
throws if the view has zero rows for that farm — which is the normal,
temporary state for up to ~60s after a new farm is created, not an
error. `unwrap()` rethrows unconditionally, so that legitimate "not
refreshed yet" state was crashing the whole page. Switched to
`.maybeSingle()` and only throw on an actual Postgres/PostgREST error;
a missing row now correctly renders as zero-value stats, same as any
other new farm.

## 2. Offline architecture — what's solid, what's missing

The offline system here is genuinely well-built for the four farmer
enterprises (poultry, dairy, coffee, small ruminants): a proper
IndexedDB event log per domain in `lib/offline-db.ts`, idempotent replay
via `eventId` through the `sync-offline-events` edge function, a
`SyncManager` pill showing pending-count, and a separate
`ConnectivityBanner` for raw online/offline state. That's the right
shape and this diff doesn't rearchitect it.

Two real bugs found and fixed in this diff:

1. **`public/sw.js` was stuck at `DB_VERSION = 2`** while
   `lib/offline-db.ts` is at `4`. Once the main thread upgraded the
   shared IndexedDB database to v4, the service worker's own `openDB()`
   started throwing `VersionError` on every call — silently, because it
   was wrapped in a `try/catch` that only logs. The fetch handler still
   returned "Saved locally. Will sync when online." regardless, so the
   failure was invisible: a false positive telling farmers their data
   was safe when it wasn't written anywhere. Fixed by matching the
   version and mirroring the store schema.
2. **The service worker was intercepting every Supabase mutation**, not
   just this app's own `/api/` routes. Because the SW sits in front of
   the page at the network layer, a failed Supabase insert (e.g. a
   direct `supabase.from('poultry_health_records').insert(...)` call)
   was getting a synthetic 202 handed back to `supabase-js` *before* the
   app's own domain-specific offline queue (`queuePoultryEvent`, etc.)
   ever got a chance to run in the calling code's catch block — because
   from `supabase-js`'s point of view, the request had "succeeded." This
   silently starved the good offline system of the failures it needs to
   see. Scoped the SW's mutation interception to same-origin `/api/`
   only; Supabase calls now fail through to the page exactly as
   `supabase-js` expects.

**Gap, not fixed by blind automation — the cooperative side has no
offline write path at all.** Factory intake, mill lots, export lots, and
farmer mapping all call `'use server'` actions directly with no offline
fallback, and washing stations are exactly the kind of rural,
patchy-signal location this matters for. I did **not** just bolt the
same queue-and-replay pattern on: `createIntakeLot` (and likely others)
derive a sequential per-factory lot number from a live `COUNT` query at
submit time, and queuing that offline risks two officers generating
colliding lot numbers the moment both devices sync — a worse problem
than the offline gap itself for a custody/traceability record.

What this diff does instead: a reusable `OfflineActionNotice` component
(same visual language as `ConnectivityBanner`) that tells the officer
plainly that a given action needs connectivity and disables the submit
button, wired into the intake-lot form as the reference implementation.
**Recommend applying the same pattern** to
`app/dashboard/cooperative/intake/mill-lots/new`,
`.../export-lots/new`, and `.../farmers/new` — same import, same JSX
block, near-zero risk. Separately, worth scoping: which cooperative
writes *are* safe to queue offline (e.g. free-text notes edits, document
metadata that doesn't need a server-derived sequence) vs. which need the
honest-block treatment — that's a per-action audit, not a one-line fix.

## 3. UX audit — prioritized

**High priority (shipped in this diff):**
- `app/buyer` and `app/trace` had no `loading.tsx` — the two most
  public-facing, trust-critical route segments in the app (a buyer
  opening a shared link, anyone scanning a passport QR code) were
  showing a blank white tab for the full server round trip. Added
  skeletons matching the existing `app/dashboard/loading.tsx` pattern.

**High priority (not yet done — recommend as next pass):**
- The commit-message/route mismatch in section 1a suggests dashboard
  route naming is a genuine source of confusion (`coffee` = individual
  farmer enterprise, `cooperative` = coop officer view of many farms —
  both deal with coffee). Consider renaming the cooperative route
  segment to something more distinct, e.g. `/dashboard/coop/*`, to make
  this class of mix-up structurally harder.
- `lib/safe-query.ts`'s `unwrap()`/`unwrapOr()` migration is explicitly
  "opt-in per file, not a codemod" (~69 page.tsx files, reference impl
  in `poultry/health` and now `coffee`). Every page still on the old
  `data || []` pattern has the same silent-failure risk this whole audit
  started from. Worth finishing that migration file-by-file, same as the
  RLS pass.
- No `loading.tsx` for `/dashboard/cooperative` or `/dashboard/poultry`
  etc. individually — they inherit `app/dashboard/loading.tsx`, which is
  fine as a default, but the cooperative shell's own top nav
  (`CoopDashboardShell`) unmounts/remounts on each navigation since it's
  rendered per-segment rather than in a shared layout — worth confirming
  intentional vs. an easy layout consolidation.

**Medium priority:**
- `AccountIssueScreen`'s "Try again" button calls Next's `reset()`,
  which re-renders the segment but does not necessarily re-run a
  server-side data fetch that failed due to something external (e.g. a
  materialized view still not granted). Consider having it fall back to
  a hard `router.refresh()` after N failed `reset()` attempts so "Try
  again" doesn't stay ineffective through the exact class of bug this
  audit found.
- Buyer/trace pages are public and unauthenticated — confirm rate
  limiting exists on the token-lookup path (a `[token]` or
  `[passportCode]` segment is inherently guessable-adjacent) separate
  from the RLS/auth work already done on the farmer side.

**Low priority / polish:**
- Cooperative sidebar and buyer/trace pages already follow the
  monochrome-dark, no-gradient, no-glassmorphism design language
  consistently — no changes recommended there.
